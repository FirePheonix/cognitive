# 3. Embeddings: Giving Tokens Meaning

You can now tokenize text. You can turn `"The cat sat"` into something like `[791, 3797, 3332]`. But those numbers still carry no meaning. Token ID 791 doesn't tell the model anything about what "The" means, or how it relates to other words.

This is where **embeddings** come in.

An embedding is a vector — a list of numbers — that represents a token. Not as an arbitrary label, but as a position in a high-dimensional space where meaning is encoded geometrically. Similar tokens end up close together. Dissimilar tokens end up far apart.

The jump from token ID → embedding vector is the moment language transforms into something a neural network can actually reason about.

---

## Why Not Just Use the Token ID Directly?

Let's be concrete about why passing the integer IDs straight into a neural network doesn't work.

If the model receives IDs 1, 2, 3 as raw numbers:

- It would interpret ID 3 as "bigger than" ID 1 — but that's meaningless. IDs are arbitrary labels, not quantities.
- The distance between ID 1 and ID 2 would equal the distance between ID 99 and ID 100 — implying they're equally related. Also meaningless.
- There's no way to express that "cat" and "kitten" should be mathematically close while "cat" and "democracy" should be far apart.

What we need instead is a representation that has no implied ordering, places similar tokens near each other, has a fixed size regardless of which token it is, and — crucially — is *learnable*. We shouldn't hardcode meanings. We should let the model discover them from data.

Embeddings deliver all of this.

---

## The Intuition: Describing Things with Multiple Numbers

Think about how you'd describe a color.

You could name it: "cerulean", "crimson", "chartreuse". Names are useful for humans but tell you nothing about similarity. "Red" and "orange" are perceptual neighbors, but their names share nothing.

Alternatively, describe any color with three numbers: RGB. Red = `(255, 0, 0)`. Orange = `(255, 165, 0)`. These are numerically close — and they really do look similar. Blue = `(0, 0, 255)` is numerically far from both — and looks completely different. The geometric distance between the numbers reflects the perceptual distance between the colors.

Embeddings do the same thing for words. Instead of 3 dimensions (R, G, B), they use hundreds or thousands. And instead of being hand-designed like RGB, the dimensions are **learned automatically from data** — the model adjusts them until they become useful for predicting language.

Here's a toy illustration. If a human were to hand-score a few words on four invented dimensions:

| Token     | Size | Fluffiness | Abstractness | Lives Indoors |
|:----------|:-----|:-----------|:-------------|:--------------|
| cat       | 2    | 8          | 0            | 9             |
| dog       | 5    | 7          | 0            | 6             |
| algorithm | 0    | 0          | 10           | 0             |
| table     | 6    | 0          | 0            | 8             |

As vectors: `cat → [2, 8, 0, 9]`, `dog → [5, 7, 0, 6]`, `algorithm → [0, 0, 10, 0]`.

Even with just 4 dimensions, `cat` and `dog` are geometrically close. Both are far from `algorithm`. Real embeddings have 512–4096 dimensions, but the principle is identical — closeness in the vector space reflects closeness in meaning.

The critical difference from this table: **nobody chooses what the dimensions represent.** The model discovers them. The resulting dimensions are abstract and not human-interpretable — but they still encode genuine semantic structure.

### What this looks like visually

Real embeddings live in 768 or 4096 dimensions — impossible to draw directly. But if we collapse them down to 3D (a technique called t-SNE or PCA), the structure becomes visible. Words cluster by meaning: animals near animals, royalty near royalty, tech concepts near tech concepts.

![Embedding space — king, queen, man, woman in vector space showing word arithmetic](/king-queen.png)

> **Reading this diagram:** Each dot is one word's embedding, projected from high-dimensional space down to 3D. Words cluster by meaning. The arrows show word arithmetic: start at *king*, subtract the *man* direction, add the *woman* direction, and you land at *queen*. That's not a trick — it's a real geometric property of trained embedding spaces.

## The Embedding Matrix: How It's Stored

Every token in the vocabulary gets its own embedding vector. All of these vectors live together in one big table called the **embedding matrix**.

If the vocabulary has 50,000 tokens and each embedding has 768 numbers, the matrix has shape `[50000, 768]` — 50,000 rows, 768 columns, one row per token.

Looking up an embedding is just indexing into this table. Token ID 791? Grab row 791. That row is a list of 768 floating-point numbers — that's the embedding. The whole operation takes one memory read.

```
Token IDs:  [791,   43678,  374]       ← from tokenizer
                ↓
Embedding matrix: each ID → one row
                ↓
Embedding vectors:
  row 791   → [0.234, -0.512, 0.891, ...]   (768 values)
  row 43678 → [0.103,  0.744, -0.321, ...]   (768 values)
  row 374   → [-0.567, 0.219, 0.455, ...]    (768 values)
```

![Embedding lookup is a gather, not a multiply. Token IDs 0 and 2 pick rows 0 and 2 of a tiny table E (vocab × d) and stack them into X (tokens × d). After this, the rest of the model only sees vectors.](/appendix-a/03-embeddings/embedding-row-lookup.png)

After this step, the integer IDs disappear. Everything that follows in the model works entirely with these floating-point vectors.

## The Geometry of Meaning: Word Arithmetic

Here's where embeddings get genuinely surprising. Because relationships are encoded as *directions* in the vector space, you can do arithmetic on meaning.

The classic example:

```
embedding("king") − embedding("man") + embedding("woman") ≈ embedding("queen")
```

The difference `king − man` captures the concept of "royalty minus male gender." Add `woman`, and you land near "queen." No rule was ever written down — this geometric structure emerged from the model seeing sentences like "the king declared" and "the queen declared" millions of times.

### Cosine similarity — measuring the angle, not the distance

Two vectors can point in the same direction even if one is longer. That's why we measure **angle** (cosine similarity) rather than raw distance. Two words that appear in identical contexts end up pointing the same way — regardless of how "big" their vectors are.

## Static vs Contextual Embeddings

There's one important limitation to know about before we move on.

The embedding lookup described above is **static**: every time you encode the word "bank", you get the exact same vector — regardless of whether you mean a financial institution or a riverbank. The same token, always the same vector.

This was a real weakness of early embedding systems like Word2Vec and GloVe. They assigned one vector per word, and that one vector had to somehow capture all possible meanings simultaneously.

Modern Transformers handle this differently. The initial embedding lookup still returns the same static vector for "bank". But then the **attention mechanism** (coming in Appendix C) modifies each token's representation based on all the other tokens around it. By the time "bank" has passed through several Transformer layers, its internal representation has been updated to reflect which sense of the word is relevant in this specific context.

- In "I deposited money in the **bank**" — the embedding shifts toward finance meaning.
- In "I sat on the river **bank**" — the embedding shifts toward geography meaning.

Both started from the same initial vector. The Transformer layers made them contextual. This is one of the core reasons why Transformers outperformed earlier models so dramatically.

The first widely used *contextual* embeddings were ELMo (Peters et al., 2018) — a deep bidirectional LSTM language model whose internal states became the word vectors. Same word, different context, different vector. Transformers then made that idea bidirectional *and* parallel.

## Before You Move On

- A token ID is just an index. An **embedding** is a learned vector that encodes the token's meaning.
- The **embedding matrix** is a table with one row per vocabulary entry. Lookup is just reading a row by index.
- At initialisation, embeddings are random noise. After training, semantically similar words end up geometrically close.
- **Word arithmetic** works because relationships get encoded as consistent directions in the vector space.
- Embeddings start **static** (same vector per token regardless of context), but Transformer layers make them **contextual**.
- The embedding matrix is a substantial fraction of a model's total parameters — vocabulary size is a genuine design tradeoff.

With tokenization and embeddings in place, you now have the full picture of how raw text becomes a form a neural network can process. Everything that follows — attention, transformer blocks, generation — operates on these floating-point vectors. The foundation is set.

## Word2Vec: Learning Embeddings from Context

The idea of a learned word vector is older than Word2Vec. Bengio, Ducharme, Vincent and Jauvin (2003) trained a neural network to predict the next word from a window of previous ones, and stored each word as a row of a shared matrix $C$. That paper is the direct ancestor of every embedding table in this book.

The static embeddings described above need to be *learned* from data somehow. The most influential *scalable* method for doing this — Word2Vec (Mikolov et al., 2013) — is worth understanding in detail, because it makes concrete what "learning from text" actually means mathematically.

The core intuition is called the **Distributional Hypothesis**: a word's meaning is defined by the company it keeps. Words that appear in similar contexts — "doctor" and "physician," "fast" and "quick" — should end up with similar vector representations. You don't need to label what any word means; you just need to observe which words tend to appear near each other.

### The Skip-gram Model

Word2Vec's Skip-gram variant learns embeddings by training on a simple prediction task: given a center word, predict the surrounding words within a context window.

![Skip-gram step 1. Sentence “the cat sat”, window m = 1. Three centers produce four training pairs: the → cat; cat → the and cat → sat; sat → cat. The only label is “these two words appeared next to each other.”](/appendix-a/03-embeddings/skipgram-step-1-window.png)

![Skip-gram step 2. One pair, by hand: center cat v = (1, 1, 0) dotted with context sat u = (0, 2, 0) scores 2. Softmax over a three-word vocab with scores 0, 1, 2 gives P(sat | cat) ≈ 0.67. The loss is −log of that number.](/appendix-a/03-embeddings/skipgram-step-2-one-pair.png)

For a center word $c$ and a context word $o$, the model defines the probability of seeing $o$ near $c$ as:

$$P(o \mid c) = \frac{\exp(u_o^\top v_c)}{\sum_{w \in V} \exp(u_w^\top v_c)}$$

Where $v_c$ is the embedding vector for the center word and $u_o$ is the embedding vector for the context word. (Each word gets *two* vectors — one for when it acts as a center word, one for when it acts as a context word.) The numerator measures how well $o$ and $c$ "match" via dot product. The denominator normalizes over the entire vocabulary $V$ so the result is a valid probability.

The training objective over a corpus with window size $m$ is to maximize the log-probability of all observed context pairs:

$$J = -\sum_t \sum_{-m \le j \le m,\ j \neq 0} \log P(w_{t+j} \mid w_t)$$

The negative sign turns maximization into minimization — standard convention for gradient descent. Intuitively: pull center-word vectors toward their actual context words; push them away from everything else.

### The Negative Sampling Shortcut

There's a computational problem. That denominator sums over the entire vocabulary — 50,000 items or more — for every single training example. Computing it is slow.

Negative Sampling solves this by turning the problem into binary classification. Instead of "predict the right word from all words," train the model to distinguish real context pairs from randomly sampled "negative" pairs. The objective becomes:

$$\log\sigma(u_o^\top v_c) + \sum_{k=1}^{K} \mathbb{E}_{w_k \sim P_n}\!\left[\log\sigma(-u_{w_k}^\top v_c)\right]$$

The first term rewards the model for scoring a real context pair $(o, c)$ highly. The second term penalizes it for scoring random noise pairs highly. You only need to evaluate $K$ noise words per step instead of 50,000 — typically $K = 5$ to $20$.

The noise distribution uses a 3/4 power smoothing to prevent ultra-frequent words (like "the" or "a") from dominating the negatives:

$$P_n(w) \propto f(w)^{3/4}$$

This raises the sampling probability of rare words and lowers it for common ones — giving the model more informative negatives to learn from.

The same year, Mikolov et al. published a follow-up that is how most people actually *run* Word2Vec: phrase tokens (`New_York`), subsampled frequent words, and a more careful negative-sampling story.

### GloVe: Global Vectors for Word Representation

GloVe (Pennington et al., 2014) takes a different angle. Word2Vec learns from local context windows one example at a time. GloVe asks: why not use the *global* co-occurrence statistics of the entire corpus directly?

Let $X_{ij}$ be the number of times word $j$ appears in the context of word $i$ across the whole corpus. GloVe's training objective is:

$$J = \sum_{i,j} f(X_{ij}) \left( w_i^\top \tilde{w}_j + b_i + \tilde{b}_j - \log X_{ij} \right)^2$$

The goal: make the dot product of two word vectors predict their log co-occurrence count. The weighting function $f(X_{ij})$ down-weights very frequent pairs (so "the the" doesn't dominate) and ignores zero-count pairs. The result combines the efficiency of local window methods with the statistical richness of the full corpus.

In practice, Word2Vec and GloVe produce embeddings with similar properties — both capture analogies, both cluster by meaning. The differences are mostly engineering tradeoffs.

### The Geometry of Meaning, Revisited

Both methods produce the famous word analogy results. The vector arithmetic works because relationships get encoded as consistent *directions*:

$$v_{\text{king}} - v_{\text{man}} + v_{\text{woman}} \approx v_{\text{queen}}$$

The vector $v_{\text{king}} - v_{\text{man}}$ captures a "royalty" direction, independent of gender. Adding $v_{\text{woman}}$ shifts along the gender axis to land near "queen." You can find the best matching word by searching for the nearest neighbor using cosine similarity:

$$d^* = \arg\max_d \cos(v_d,\ v_b - v_a + v_c)$$

This works for country–capital pairs (France–Paris, Germany–Berlin), grammatical relationships (walk–walking, swim–swimming), and many semantic relationships. None of this was programmed in — it emerged purely from which words appeared near which other words.

> **The fundamental limitation:** A word like "bank" gets one vector — it can't simultaneously represent "financial institution" and "riverbank." Whatever the training data's balance of usages is, that's what the single vector reflects. This is the key weakness of static embeddings. The fix — contextual representations where the same word gets a *different* vector depending on the surrounding text — is exactly what Transformers provide. Word2Vec was the stepping stone that made the path visible: it proved that meaning could be geometry, and that geometry could be learned from raw text.

# 17.5 Latency Analysis

Agent latency is not a single number — it's the sum of multiple sequential operations. Understanding where time is spent is the prerequisite to reducing it.

## Where Latency Comes From

```
User sends request
      │
      ▼
[LLM Call 1: tool selection]          ← TTFT + full generation
      │
      ▼
[Tool Execution: e.g., web search]    ← network round-trip + processing
      │
      ▼
[LLM Call 2: interpret results]       ← TTFT + full generation
      │
      ▼
[Tool Execution: e.g., fetch_url]     ← another network round-trip
      │
      ▼
[LLM Call 3: generate response]       ← TTFT + streaming
      │
      ▼
User receives response
```

Typical distribution for a 3-step research agent:

| Component | Typical Time | % of Total |
|-----------|-------------|------------|
| LLM calls (combined) | 0.8–1.5s | 25–40% |
| Tool executions | 1.5–4.0s | 60–75% |
| Routing/overhead | 50–100ms | 2–5% |

**The tool is usually the bottleneck, not the model.**

## Key Latency Metrics

### TTFT — Time to First Token

The time from request submission to when the first token arrives in the stream. Users perceive this as "how long until the agent starts responding."

```python
def measure_ttft(client, messages: list) -> float:
    start = time.perf_counter()
    first_token_time = None

    with client.messages.stream(
        model="claude-opus-4-5",
        messages=messages,
        max_tokens=1000,
    ) as stream:
        for text in stream.text_stream:
            if first_token_time is None:
                first_token_time = time.perf_counter()
            break  # Only need the first token

    return (first_token_time - start) * 1000  # ms
```

### Total Streaming Time

From TTFT to last token. Proportional to output length — minimize output tokens if latency matters.

### Tool Execution Time

Tracked per tool. Identify which tools are slow:

```python
# From span data
tool_latencies = defaultdict(list)
for span in trace.spans:
    if span.kind == "tool":
        tool_latencies[span.name].append(span.duration_ms)

# Average latency per tool
for tool, latencies in tool_latencies.items():
    avg = sum(latencies) / len(latencies)
    p95 = sorted(latencies)[int(len(latencies) * 0.95)]
    print(f"{tool}: avg={avg:.0f}ms  p95={p95:.0f}ms")
```

## Parallel Tool Execution

When an agent needs multiple independent tool results, run them in parallel. From `atlas-agents/ch05_state_graphs/online/parallel_fanout.py`:

```python
import asyncio

async def parallel_research(queries: list[str]) -> list[str]:
    """
    Fan out to multiple search queries simultaneously.
    N sequential calls → 1 parallel round-trip.
    """
    tasks = [search_web(q) for q in queries]
    results = await asyncio.gather(*tasks)
    return results

# Sequential (bad): 3 × 800ms = 2,400ms
# Parallel (good):  1 × 800ms = 800ms  (3× faster)
```

LangGraph supports parallel branches natively — define independent nodes and connect them through a fan-out edge.

## The Latency Breakdown View

Useful aggregation for optimization decisions:

```python
def latency_breakdown(traces: list[Trace]) -> dict:
    """Summarize where time is spent across a set of traces."""
    llm_times = []
    tool_times = defaultdict(list)

    for trace in traces:
        llm_total = sum(s.duration_ms for s in trace.spans if s.kind == "llm")
        llm_times.append(llm_total)

        for span in trace.spans:
            if span.kind == "tool":
                tool_times[span.name].append(span.duration_ms)

    return {
        "llm_avg_ms": mean(llm_times),
        "tools": {
            name: {"avg": mean(times), "p95": percentile(times, 95)}
            for name, times in tool_times.items()
        },
    }
```

## Latency Optimization Strategies

| Strategy | When to Apply | Typical Gain |
|----------|--------------|-------------|
| Parallel tool execution | Multiple independent tools needed | 40–70% reduction |
| Smaller model for classification | Safety/routing decisions don't need full capability | 50–80% on that step |
| Cache frequent tool results | Same queries repeated across users | Eliminates tool latency |
| Streaming output | Long responses, user-facing | Improves perceived latency |
| Reduce context window | Trim tool results before injection | 10–30% on LLM calls |

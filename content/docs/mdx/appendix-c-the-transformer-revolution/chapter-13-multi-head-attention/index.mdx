# 13. Multi-Head Attention

Chapter 12 built one attention operation: every token produces one query, compares it with every key, and gets back one weighted average of values. That's a real limitation. A weighted average is a single blend, so a token can only follow **one kind of relationship at a time**.

Look at *it* in "The animal didn't cross the street because it was too tired." To understand *it*, a model wants several things at once: which noun *it* refers to (*animal*), which verb it belongs to (*was*), what came just before it (*because*), and roughly what the sentence is about. One softmax has to choose how to split a single unit of weight across all of those, and the answer ends up a muddy compromise.

**Multi-head attention** (Vaswani et al., 2017) runs several smaller attention operations side by side, each with its own projections, so each can look for something different, and then merges what they found. It is the version of attention every Transformer actually uses.

---

## The idea

Instead of one attention with $d_{\text{model}}$-dimensional queries and keys, use $h$ **heads**, each working in a smaller $d_k = d_{\text{model}} / h$ dimensional space. In the original Transformer, $d_{\text{model}} = 512$ and $h = 8$, so each head has $d_k = 64$.

Each head has its own three projection matrices, so it asks its own question:

$$
\text{head}_i = \operatorname{Attention}\!\left( X W_i^{Q},\; X W_i^{K},\; X W_i^{V} \right),
\qquad W_i^{Q}, W_i^{K}, W_i^{V} \in \mathbb{R}^{d_{\text{model}} \times d_k}
$$

Then the head outputs are placed side by side and mixed by one more matrix:

$$
\operatorname{MultiHead}(X) = \operatorname{Concat}\!\left(\text{head}_1, \dots, \text{head}_h\right) W^{O},
\qquad W^{O} \in \mathbb{R}^{h d_k \times d_{\text{model}}}
$$

Each head produces an $n \times d_k$ output; concatenating $h$ of them gives $n \times d_{\text{model}}$ again, and $W^O$ maps it back into the model's space. Same shape in, same shape out.

![Multi-head attention data flow with d_model = 512, h = 8, d_k = 64. The input X (batch, seq, 512) fans out to eight heads, each with its own W_Q, W_K, W_V projecting 512 → 64. Under each head is a small attention map showing a different pattern: head 1 looks at the previous word, head 2 links "it" to "animal", head 3 looks at the first token, head 8 averages the context. Their outputs are concatenated (8 × 64 = 512), multiplied by W_O (512 × 512) to mix the heads, giving an output of the same shape as X. Side panels give the equations and explain that the total parameters and FLOPs equal one 512-dimensional head.](/appendix-c/13-multi-head-attention/multi-head-overview.png)

Why does splitting help? Each head's queries and keys live in their own 64-dimensional subspace, learned independently. One head can learn "a pronoun's query matches a noun's key", another "every token's query matches the key of the token just before it". Each runs its own softmax, so they don't have to share one unit of attention. The output projection then combines their findings into one vector per token.

---

## It costs (almost) nothing extra

Splitting doesn't multiply the work; it divides one big attention into $h$ narrow ones. Count it for $d_{\text{model}} = d$, $h$ heads, $d_k = d/h$, sequence length $n$:

| | one head, $d_k = d$ | $h$ heads, $d_k = d/h$ |
|---|---|---|
| Q, K, V projection weights | $3d^2$ | $h \cdot 3 \cdot d \cdot (d/h) = 3d^2$ |
| output projection $W^O$ | $d^2$ | $d^2$ |
| score multiplications $QK^{\top}$ | $n^2 d$ | $h \cdot n^2 (d/h) = n^2 d$ |
| mixing $AV$ | $n^2 d$ | $n^2 d$ |
| attention maps stored | $n^2$ | $h \cdot n^2$ |

Parameters are $4d^2$ either way, and the matrix-multiply FLOPs are identical. The one thing that grows is the number of $n \times n$ attention maps — $h$ of them instead of one. During training those maps are saved for the backward pass, which is part of why FlashAttention (Chapter 12), which never stores them, matters so much for long contexts. The softmax also runs $h$ times, but that is cheap next to the matrix multiplies.

Left: a table comparing one head with d_k = 512 against 8 heads with d_k = 64: Q, K, V projections 3·512² both ways, output W_O 512² both ways, score matmuls n²·512 both ways, AV n²·512 both ways, but attention maps stored 1 × n² versus 8 × n². Right: W_O drawn as eight horizontal slabs W_O^(1)…W_O^(8); each head's output multiplies only its own slab and the results are summed, so Concat(head_1…head_h) W_O = Σ_i head_i W_O^(i), the residual-stream view used in interpretability work (Elhage et al., 2021).](/appendix-c/13-multi-head-attention/same-cost-and-wo.png)

### What $W^O$ really does

The "concatenate, then multiply" step has a cleaner reading. Split $W^O$ into $h$ horizontal slabs of $d_k$ rows each, $W^O = \left[W^{O(1)}; \dots; W^{O(h)}\right]$. Matrix multiplication by blocks gives

$$
\operatorname{Concat}\!\left(\text{head}_1, \dots, \text{head}_h\right) W^{O} \;=\; \sum_{i=1}^{h} \text{head}_i\, W^{O(i)}
$$

So multi-head attention is literally **$h$ independent attention layers whose outputs are added together**. Each head reads from the token vectors, computes its own weighted average, projects it with its own $W^{O(i)}$, and adds the result back. "Concatenate" is just bookkeeping. This is the view that mechanistic-interpretability research uses (Elhage et al., 2021): every head *reads from* and *writes to* a shared residual stream (Chapter 15) independently.

## The reshape trick: all heads in one matrix multiply

You could implement this with a Python loop over eight small attention modules. Nobody does, because GPUs are fastest on a few large matrix multiplies, not many small ones. Instead:

1. **One projection for all heads.** Stack the eight $512 \times 64$ matrices $W_i^Q$ side by side into one $512 \times 512$ matrix $W^Q$. Then $Q = XW^Q$ computes every head's queries at once; columns 0–63 belong to head 1, columns 64–127 to head 2, and so on.
2. **`.view(B, T, h, d_k)`** — cut each 512-vector into 8 chunks of 64. No data moves; the same memory is read differently.
3. **`.transpose(1, 2)`** — move the head axis next to the batch axis: `(B, h, T, d_k)`. Now "heads" behaves like extra batch entries.
4. **Attention as usual.** `Q @ K.transpose(-2, -1)` is a batched matrix multiply over $B \cdot h$ independent problems, giving scores of shape `(B, h, T, T)`.
5. **Merge back:** transpose back, reshape to `(B, T, 512)`, multiply by $W^O$.

![The reshape trick: eight heads, one matrix multiply. Step 1: one projection Q = X W_Q with W_Q of shape 512 × 512 — each token's 512-number query is eight 64-number head chunks side by side. Step 2: .view(B, T, h, d_k) cuts each vector into 8 chunks, (B, T, 512) → (B, T, 8, 64), with no data moving. Step 3: .transpose(1, 2) swaps token and head axes to (B, 8, T, 64). Step 4: attention for all heads at once as a batched matmul, scores (B, 8, T, T). Step 5: transpose back, reshape to (B, T, 512) and multiply by W_O; .contiguous() or .reshape is needed because the transpose left memory in head-major order.](/appendix-c/13-multi-head-attention/split-heads-reshape.png)

Parameters and matrix-multiply work stay fixed however you split the 512 dimensions. Only the number of stored attention-map entries grows with the head count. That's also why heads can't be made arbitrarily narrow: with $d_k = 8$, each head's score matrix $QK^{\top}$ has rank at most 8, which limits the patterns a head can express (Bhojanapalli et al., 2020). In practice $d_k$ = 64 or 128 is the sweet spot, and most models scale up by adding heads rather than shrinking them.

## What heads actually learn

Nobody tells a head what to do. Yet when researchers probe trained Transformers, many heads turn out to do recognisable, interpretable jobs:

- **Previous-token heads** attend to the token right before the current one — a building block for reading short phrases.
- **Induction heads** (Olsson et al., 2022) implement copying from context: seeing "Harry" again, attend to whatever followed the *last* "Harry" and predict it ("Potter"). They form from a previous-token head in one layer working with a matching head in a later layer, and their appearance during training coincides with a sudden jump in the model's ability to learn from examples in its prompt — **in-context learning**.
- **Syntactic heads** (Clark et al., 2019; Voita et al., 2019) track specific grammatical relations — verbs to their subjects, determiners to their nouns, objects to their verbs — often more accurately than simple baselines.
- **Coreference heads** link pronouns to the nouns they refer to.
- **Attention sinks** (Xiao et al., 2023): many heads put most of their weight on the very first token whenever they have nothing useful to look at. Softmax weights must sum to 1, so a head that "wants" to attend nowhere parks its weight somewhere harmless. This turned out to matter in practice — streaming models that drop the first token from their cache fall apart, and keeping it (StreamingLLM) fixes them.
- **Broad or averaging heads**, common in early layers, spread their weight evenly and build a bag-of-words summary of the context.

### But not every head matters

Michel, Levy & Neubig ("Are Sixteen Heads Really Better than One?", 2019) removed heads from trained models one at a time. Many could be deleted with almost no loss, and some layers kept working with a single head left. Voita et al. (2019) found that a handful of specialised heads did most of the work in a translation model, and that the rest could be pruned. The lesson isn't that multi-head attention is wasteful. Having many heads gives the model **room to specialise** during training — it just doesn't use all of that room equally in the end.

Interpreting heads also has limits: as Chapter 11 noted, attention weights show where information is *read from*, not *why* the model decided something. Modern interpretability work studies heads together with what they write back (their $W^{O(i)}$ slab), which is exactly the sum view above.

## Sharing keys and values: MQA and GQA

Multi-head attention costs the same as one head during training. During **generation** it has a different cost, and that cost drove the biggest change to attention since 2017.

Chapter 12 introduced the **KV cache**: while generating, every past token's keys and values are stored so they don't have to be recomputed for each new token. With $L$ layers, $h_{kv}$ key/value heads of size $d_{\text{head}}$, a context of $n$ tokens, and $b$ bytes per number, the cache for one sequence is

$$
\text{KV cache bytes} = 2 \cdot L \cdot h_{kv} \cdot d_{\text{head}} \cdot n \cdot b
$$

The 2 is for keys and values. For Llama-2-7B (32 layers, 32 heads of 128, fp16) that's 0.5 MiB per token — 2 GiB for a 4,096-token conversation, per user. At long contexts and large batches the cache, not the weights, fills GPU memory, and reading it at every step limits generation speed.

**Multi-query attention** (MQA; Shazeer, 2019) keeps all $h$ query heads but gives them **one shared** key head and value head. The cache shrinks by a factor of $h$. Quality drops a little, and training can be less stable.

**Grouped-query attention** (GQA; Ainslie et al., 2023) is the compromise: split the query heads into $g$ groups and give each group one key/value head. With 32 query heads and 8 KV heads, every 4 query heads share one key/value pair. Quality is close to full MHA, the cache shrinks 4×, and existing MHA checkpoints can be converted by averaging their KV heads and briefly fine-tuning. Llama 2 70B, Llama 3, Mistral and Qwen all use GQA.

Each query head still has its own $W^Q_i$, so it still asks its own question; it just reads the answer from a key/value table shared with its group.

The output shape never changes; what changes is how much has to be cached per token. GQA with 2 KV heads caches a quarter of what MHA does here; MQA an eighth.

The idea keeps going. DeepSeek-V2 (2024) introduced **multi-head latent attention** (MLA), which caches one small compressed vector per token and reconstructs every head's keys and values from it, shrinking the cache further while keeping per-head keys and values.

## Quick recap

- One attention head produces one weighted average per token, so it can follow only one relationship at a time. **Multi-head attention** runs $h$ heads in parallel, each with its own $W_i^Q, W_i^K, W_i^V$ in a $d_k = d_{\text{model}}/h$ subspace.
- $\operatorname{MultiHead}(X) = \operatorname{Concat}(\text{head}_1, \dots, \text{head}_h)\,W^O$, which equals $\sum_i \text{head}_i W^{O(i)}$: $h$ independent heads whose outputs are **added**.
- Parameters ($4d^2$) and matrix-multiply FLOPs are the same as one full-width head; only the number of stored $n \times n$ attention maps grows with $h$.
- In practice all heads run as **one** batched matrix multiply via `view` → `transpose` → attention → `transpose` → `reshape` → $W^O$.
- Trained heads specialise — previous-token, induction, syntactic, coreference, attention sinks — but many can be pruned afterwards.
- During generation the **KV cache** dominates memory. **MQA** shares one K/V head across all queries, and **GQA** shares one per group, cutting the cache 4–8× with little quality loss. That's why modern LLMs use GQA.

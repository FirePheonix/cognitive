# 8. The Problem with Sequential Data

The network from Chapter 7 can learn. It gets a batch of inputs, makes predictions, calculates how wrong it was, and updates its weights accordingly. Given enough examples and enough training time, it gets quite good at pattern recognition.

So why can't you just use that kind of network for language?

The problem is in how it sees its input.

---

## The Network Doesn't Know About Order

A feed-forward network processes all its inputs at the same time, independently. It has no concept of "position 1 came before position 2." To the network, a bag of input features is a bag of input features — order is invisible.

For some tasks, that's fine. If you're predicting whether a house is expensive based on square footage, number of bedrooms, and location, the order in which you list those features doesn't matter.

But language is almost entirely about order.

```
"Dog bites man"
"Man bites dog"
```

Same three tokens. Different order. Completely different meaning — and newsworthy for entirely different reasons.

These are different token IDs, so a network would distinguish them. But the deeper problem isn't that specific pair — it's that a feed-forward network has no mechanism for encoding *relationships between positions*. It doesn't know that "subject of the sentence" is typically the first noun, that "not" negates what immediately follows it, or that the pronoun "they" refers back to a noun introduced several tokens ago.

---

## The Naïve Approach and Why It Fails

The most naïve fix is to concatenate token embeddings in order and feed them into a feed-forward network. For a 4-token sentence:

```
[emb_token1 | emb_token2 | emb_token3 | emb_token4]  →  feed-forward network  →  prediction
```

This preserves order — position 1's embedding goes into the first slot, position 2 into the second slot. And for that specific length of sentence, it works fine.

But there are two fatal problems.

Two fatal flaws:

1. **Fixed length.** Real sentences vary wildly in length. A fixed-size input layer can't handle that. GPT processes sequences up to 4096 tokens. Building a different model for every length from 1 to 4096 is obviously not viable.

2. **No weight sharing.** The network assigns completely separate weights to position 1 and position 3. If "cat" appears at position 1, the model uses one weight block. If "cat" appears at position 3, it uses a different weight block. Those blocks don't talk to each other. The model has to independently re-learn the semantics of "cat" for every possible position. It can't generalize.

## Why This Matters: Long-Range Dependencies

Even setting aside the fixed-length problem, there's a deeper issue with position-blind processing. Consider:

```
"The trophy didn't fit in the suitcase because it was too big."
```

What does "it" refer to? The trophy. You know this because "too big" makes sense as a description of the trophy (which didn't fit) rather than the suitcase (which is the thing being fitted into).

That's a dependency that spans seven tokens. The model needs to look back from "big" to connect it correctly to "trophy." A network that processes tokens independently has no way to build that connection.

A language model needs to handle these. To do that, it needs **memory** — some way to carry information from earlier positions forward and make it available when processing later positions.

## What a Sequence Model Needs

At this point the problem is clear. A network for language needs to satisfy three things that a plain feed-forward network doesn't:

**1. Variable-length input.** Sentences are 3 tokens or 300 tokens or 3000 tokens. The architecture has to handle all of these with the same set of weights.

**2. Position sensitivity.** "Dog bites man" and "Man bites dog" are not the same. The model needs to know *where* each token appears, not just *what* it is.

**3. Long-range memory.** A pronoun early in a sentence might be resolved by its antecedent dozens of tokens back. The model needs to maintain and access information across arbitrary spans.

The natural architectural response to requirements 1 and 2 is the same idea: **process tokens one at a time, in order, using the same weights at every step**. This is weight sharing over time — the network doesn't need separate weights for each position, because it applies the same computation at each step. It also handles variable length naturally, because you just keep going until the sequence ends.

That's the core idea behind Recurrent Neural Networks.

## A Toy Demonstration of Why Order Matters

Before we move to RNNs, let's make the failure mode concrete with an actual experiment. We'll take a tiny language modeling task and show that a network with no positional awareness genuinely cannot learn it.

## The Key Insight: Process Tokens One at a Time

The way out of this corner is to stop thinking about "a sentence as one big fixed-size input" and start thinking about "a sequence of decisions made one step at a time."

Instead of feeding all tokens simultaneously, read them one at a time — left to right, in order. At each step, the network has access to the current token *and* a running summary of everything it's seen so far. This running summary is the **hidden state**.

```
Step 1: see "The"  →  update hidden state  →  output (predict next)
Step 2: see "cat"  →  update hidden state  →  output (predict next)
Step 3: see "sat"  →  update hidden state  →  output (predict next)
...
```

The same network weights apply at every step. The hidden state carries forward what matters from earlier steps. Variable-length sequences work naturally — you just stop when the sequence ends.

This is the design principle behind Recurrent Neural Networks, which is exactly where the next chapter picks up.

---

## Quick Recap

- Feed-forward networks process all inputs simultaneously and independently — they have no notion of order.
- Language is deeply sequential: "Dog bites man" ≠ "Man bites dog."
- A naïve fix (concatenate embeddings in order) fails on two counts: **fixed length** and **no weight sharing across positions**.
- Meaningful language tasks require **long-range dependencies** — information from many tokens back must influence the current prediction.
- A viable sequence model needs: variable-length handling, position sensitivity, and long-range memory.
- The key architectural insight: **process tokens one at a time, in order, with the same weights at every step, maintaining a running hidden state** that accumulates context.

That's the recurrent neural network. Let's see exactly how it works — and where it runs into trouble.

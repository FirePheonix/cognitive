# 2.5 Context Window Management

The context window is the model's working memory. Everything the model can "see" — the system prompt, conversation history, retrieved documents, tool results — lives in this window. When the window is full, something has to give. When the window is empty, the model is flying blind.

Managing the context window well is one of the highest-leverage skills in AI engineering.

---

## The Numbers

| Model | Context Limit | Approximate Words | Cost of Filling It |
|-------|--------------|------------------|-------------------|
| GPT-4o | 128K tokens | ~96,000 words | High |
| Claude 3.5 Sonnet | 200K tokens | ~150,000 words | High |
| Gemini 1.5 Pro | 1M tokens | ~750,000 words | Very high |
| Llama 3 70B | 8K tokens | ~6,000 words | Low |

The large context windows of frontier models are genuinely useful. But filling them costs money and increases latency. A 100K-token prompt costs roughly 10x what a 10K-token prompt costs, and takes longer to process.

The goal is not to minimize context — it's to include **exactly what the model needs for the next step, and nothing more**.

---

## The Progressive Disclosure Pattern

A common mistake in early AI systems is dumping all potentially relevant information into the context upfront:

```
❌ Bad: Load all 200 pages of documentation at the start of every session
✅ Good: Let the agent request specific docs on demand
```

Progressive disclosure means the agent starts with a high-level overview and requests detailed reference material only when needed. This pattern is implemented in `atlas-agents/ch15_agent_harness/harness.py` through the `read_reference()` tool:

```python
def read_reference(section: str) -> str:
    """
    Load a specific section of reference documentation on demand.
    Called by the agent when it needs details about a specific topic.
    Returns the content of that section, typically 500-2000 tokens.
    """
    doc_path = REFERENCE_DOCS_DIR / f"{section}.md"
    if not doc_path.exists():
        return f"No reference doc found for '{section}'. Available: {list_available_sections()}"
    return doc_path.read_text()
```

The agent's system prompt tells it: "Reference documentation is available via `read_reference(section)`. Do not assume you know the API details — look them up." 

This keeps the initial context lean. The agent loads documentation lazily, only when it actually needs it.

## What Should Always Be in Context

Some things should be present on every call:

- **Identity and instructions** — The agent needs to know who it is and what workflow to follow
- **Current task** — What the agent is trying to accomplish right now
- **Most recent tool results** — The output of the last action, so the agent can react to it
- **Active errors** — If something failed, the failure message must be in context

Some things should be loaded on demand:

- Reference documentation
- Historical conversation turns (summarize instead)
- Full file contents (load only the relevant section)
- Detailed schemas (load when about to use them)

## Token Budget Management

When building the context, track your token budget explicitly:

```python
class ContextBuilder:
    def __init__(self, max_tokens: int, tokenizer):
        self.max_tokens = max_tokens
        self.tokenizer = tokenizer
        self.sections: list[tuple[int, str]] = []  # (priority, content)
    
    def add(self, content: str, priority: int = 5):
        tokens = len(self.tokenizer.encode(content))
        self.sections.append((priority, tokens, content))
    
    def build(self) -> str:
        # Sort by priority (higher = more important), fill up to budget
        sorted_sections = sorted(self.sections, key=lambda x: -x[0])
        result = []
        used = 0
        for priority, tokens, content in sorted_sections:
            if used + tokens <= self.max_tokens:
                result.append((priority, content))
                used += tokens
        # Restore original order
        result.sort(key=lambda x: -x[0])
        return "\n\n".join(content for _, content in result)
```

Give your system prompt the highest priority. Give retrieved docs medium priority. Give conversation history lower priority — it can be compressed if needed.

## The Cost-Quality Tradeoff in Practice

A concrete example: you're building a coding assistant with 128K token capacity. You could:

**Option A — Fill the window**
Load the entire repository (80K tokens) + full documentation (30K tokens) + conversation history (10K tokens) = 120K tokens. Model has maximum information. Cost: ~$0.12 per request at GPT-4o pricing.

**Option B — Targeted context**
Load only the three relevant files (3K tokens) + relevant doc sections loaded on demand (2K tokens) + compressed history (1K tokens) = 6K tokens. Cost: ~$0.006 per request.

Option B costs 20x less. For most requests, the model doesn't need the full repository — it needs the three files relevant to the current task. Retrieval and progressive disclosure let you get Option A quality at Option B cost, most of the time.

The exception: tasks where you genuinely need holistic understanding of a large codebase. For those, the large context window earns its cost. For the majority of targeted tasks, it doesn't.

# 2.11 Loop Engineering vs Graph Engineering

There are two ways to give an AI agent control flow: a loop or a graph.

The loop is simple: while the task isn't done, call the model, execute the result, repeat. The graph is explicit: define nodes (states), edges (transitions), and conditions, then let a framework like LangGraph route execution between them.

Neither is universally better. They solve different problems, and knowing when to reach for each one is one of the more practical judgment calls in agent engineering.

---

## Loop Engineering

A loop-engineered agent is, at its core, a `while` loop with a termination condition:

```python
def run_agent(task: str, max_iterations: int = 20) -> str:
    messages = [build_system_prompt(task)]
    
    for iteration in range(max_iterations):
        response = call_model(messages)
        action = parse_action(response)
        
        # Termination condition
        if action.type == "finish":
            return action.result
        
        # Execute the action
        result = execute_tool(action)
        
        # Structured feedback back into context
        messages.append({"role": "assistant", "content": response})
        messages.append({"role": "tool", "content": result})
        
        # Compact context before next cycle
        if should_compress(messages):
            messages = compress_history(messages)
    
    # Escalation: couldn't finish in max_iterations
    return escalate("Max iterations reached", messages)
```

That's the whole structure. The model decides what to do, the loop executes it and feeds the result back, and this continues until either the model says "finish" or the iteration limit is hit.

Loop engineering is the **third discipline** in the book's arc:
1. Prompt engineering (2022–2024): human reads every output
2. Context/harness engineering (2025): the environment does the heavy lifting
3. Loop engineering (2026): the system runs itself

In loop engineering, the agent is genuinely autonomous for the duration of a task. It only escalates when it's genuinely stuck, not every time it wants confirmation.

## The Five Parts of an Engineered Loop

A well-built agentic loop has five components:

### 1. Trigger
What starts the loop. Could be a user request, a scheduled job, a webhook, or another agent.

### 2. Termination Condition
What ends the loop. Multiple conditions, in priority order:
- Model returns `action: "finish"` — success path
- Max iterations reached — safety limit
- Error rate exceeds threshold — circuit breaker
- Human override — escalation trigger

Without explicit termination conditions, loops can run indefinitely and rack up costs.

### 3. Structured Feedback
Each iteration must produce feedback that the next iteration can act on. Tool results, test outputs, error messages — all fed back as structured data, not prose summaries.

```python
# ✅ Structured feedback — model can parse and react
{"tool": "run_tests", "result": {"passed": 12, "failed": 2, "errors": ["AssertionError in test_auth.py:88"]}}

# ❌ Unstructured feedback — model gets vague information
"The tests had some issues with the auth module."
```

### 4. Context Compaction
Before each iteration, prune the history. Failed attempts that were retried become one-line lessons. Successful steps get summarized. Only the current state and recent actions stay in full detail.

From `atlas-agents/ch20_loop_engineering`:
> "Prune history before each cycle; failed attempts become one-line lessons."

### 5. Escalation Logic
When to stop trying and ask a human. The agent should escalate when:
- It has tried the same approach more than N times
- It encounters an action outside its tool authorization
- The task requires information it cannot retrieve
- A risk threshold is exceeded

```python
def should_escalate(trajectory: list[TrajectoryStep]) -> bool:
    recent = trajectory[-5:]
    
    # Same tool called with same args 3+ times = stuck
    if len({(s.tool, str(s.args)) for s in recent}) <= 2 and len(recent) >= 3:
        return True
    
    # Error rate too high
    error_rate = sum(1 for s in recent if not s.success) / len(recent)
    if error_rate > 0.6:
        return True
    
    return False
```

## Graph Engineering

Graph-engineered agents use explicit state machines — nodes represent states or actions, edges represent transitions, and the framework routes between them based on conditions.

```python
# LangGraph example
from langgraph.graph import StateGraph

graph = StateGraph(AgentState)

graph.add_node("plan", plan_step)
graph.add_node("execute", execute_step)
graph.add_node("review", review_step)
graph.add_node("human_approval", human_approval_step)

graph.add_edge("plan", "execute")
graph.add_conditional_edges("execute", route_after_execute, {
    "success": "review",
    "needs_approval": "human_approval",
    "failure": "plan",  # retry
})
graph.add_edge("review", END)
graph.add_edge("human_approval", "execute")
```

This structure makes the control flow *explicit and visualizable*. You can draw it as a diagram. Every possible path through the agent is defined in advance.

## When to Use Which

| Use Loop Engineering when... | Use Graph Engineering when... |
|------------------------------|-------------------------------|
| The next step depends on the previous result | You need guaranteed human-in-the-loop at specific points |
| The workflow is open-ended or exploratory | You have parallel execution branches |
| You want to move fast and iterate | Compliance requires auditable, explicit control flow |
| The task is single-threaded | You need visualization of agent state |
| You're building a new agent from scratch | You're integrating into an existing LangGraph ecosystem |

The loop is simpler, faster to build, and easier to debug. The graph is more explicit, more controllable, and better suited for regulated environments or complex multi-agent coordination.

## How this is talked about in public

The split is the same line Anthropic drew in [*Building effective agents*](https://www.anthropic.com/engineering/building-effective-agents): **workflows** are predefined code paths; **agents** are a model directing its own process. Their advice is still the right default — find the simplest structure that works, and only add topology when a single call (or a single loop) is demonstrably not enough. Anthropic's *orchestrator-workers* pattern is the graph picture people keep redrawing: one model breaks the job up, specialists run, results come back.

On the Claude Code team, a loop is an agent repeating a cycle of work until a stop condition is met. Their [getting-started-with-loops](https://claude.com/resources/articles/getting-started-with-loops) note splits loops by trigger:

| Loop | You hand off | Reach for |
|------|----------------|-----------|
| Turn-based | The check | A user prompt; Claude stops when it thinks it's done |
| Goal-based | The stop condition | `/goal` — tests pass, score ≥ 90, stop after N tries |
| Time-based | The trigger | `/loop`, `/schedule` — recurring or watching an external system |
| Proactive | The prompt itself | Event or routine; no human in the room |

Addy Osmani's *Loop Engineering* popularized a close taxonomy (heartbeat, cron, hook, goal). The line that stuck, from Boris Cherny, is: *I don't prompt Claude anymore. I write loops that prompt Claude.*

Graphs showed up in public as a reaction, not a replacement. Peter Steinberger's July 2026 question — "Are we still talking loops or did we shift to graphs yet?" — and Hamel Husain's "Loop Engineering Is Dead. Enter Graph Engineering" named a practice LangGraph, AutoGen, and Anthropic's orchestrator-workers pattern had already been doing: specialized nodes, shared state, inspectable edges. A useful correction from that wave ([Dev Compass](https://devcompass.hashnode.dev/loop-engineering-vs-graph-engineering-part-1), [PALO IT](https://www.palo-it.com/en/blog/loop-and-graph-engineering)): **a loop is a graph with one node that points at itself.** Graph engineering composes loops. It does not retire them.

Carlos E. Perez's control-theory version is worth keeping in view: a single loop fails by Goodhart (it will game its own metric), by never questioning its reference, by fighting neighboring loops, and by measurement decay. A graph of loops can watch, constrain, and audit other loops — but only if some edges still touch reality (tests that actually ran, customers who actually stayed). A graph of agents grading each other is "everything is consistent and nothing is verified."

The picture that keeps showing up: one generalist Claude cycling until done, versus one orchestrator Claude dispatching other Claudes on *different lines* — solid dispatch, thick fan-out, dashed bounded retry, dotted escalate-to-human. PALO IT's minimal graph is four things a loop leaves implicit: a guarded route, a deterministic gate, a bounded retry, and a human node.

## The Practical Starting Point

Start with a loop. It covers 80% of agent use cases. If you find yourself needing:
- Hard checkpoints where a human must approve before proceeding
- True parallel execution (not just sequential tool calls)
- Complex branching that a termination condition can't capture

...then migrate the relevant parts to a graph.

The book's `atlas-agents/ch20_loop_engineering` implementation is a fully developed loop-engineered agent. By the time you reach Chapter 20, you'll have built every component from scratch — the harness, the memory, the compression, the escalation logic — and you'll understand exactly why the loop is structured the way it is.

# 17. LoRA — Parameter-Efficient Fine-Tuning

Fine-tuning a 7B-parameter model the naive way — updating every weight — requires holding a copy of every weight in GPU memory, plus gradients, plus optimizer states. With Adam, that's roughly:

```text
Memory required for full fine-tuning:

  Model weights (FP16):   2 bytes × N params
  Gradients:              2 bytes × N params
  Adam m  (FP32):         4 bytes × N params   ← first moment
  Adam v  (FP32):         4 bytes × N params   ← second moment
  ─────────────────────────────────────────────
  Total:                 12 bytes × N params

  LLaMA-7B  (7B params):  12 × 7,000,000,000 = ~84 GB
  LLaMA-70B (70B params): 12 × 70B           = ~840 GB
```

Most people don't have 84GB of GPU memory, let alone 840GB. LoRA (Low-Rank Adaptation) solves this. The core idea is to freeze the original weights completely and introduce tiny trainable matrices alongside them. You train only those — often 100× fewer parameters — and get competitive results.

---

## The Key Observation: Weight Updates Are Low-Rank

When you fine-tune a model, the update to each weight matrix `ΔW` isn't random — it tends to live in a low-dimensional subspace. The claim: you don't need to update all `d × d` values to change what the matrix does. A rank-`r` approximation where `r << d` is often sufficient.

**Low-rank matrix review:**

```text
Full weight matrix W:  shape (d_out, d_in) = (4096, 4096)
                       Contains 16,777,216 numbers

Low-rank decomposition:
  W ≈ W + A @ B
  where:
    A: shape (d_out, r)  = (4096, 16)    — 65,536 numbers
    B: shape (r, d_in)   = (16, 4096)    — 65,536 numbers
    A @ B: shape (d_out, d_in) = (4096, 4096)  — but RANK r=16

  Total LoRA params: 65,536 + 65,536 = 131,072
  vs. full update:   16,777,216 params
  Compression:       128× fewer parameters to train
```

---

## The LoRA Forward Pass

During the forward pass, the output is the sum of the frozen original path and the trainable LoRA side path:

```text
Without LoRA:
  h = W @ x
      ^─── frozen original weight

With LoRA:
  h = W @ x  +  (alpha/r) * A @ (B @ x)
      ^───────   ^──────────────────────
      frozen     trainable side path
      path       (A and B are the only learned params)

  where:
    W:     (d_out, d_in)  — FROZEN, not updated
    B:     (r, d_in)      — trainable, initialized to ZERO
    A:     (d_out, r)     — trainable, initialized randomly
    alpha: scalar hyperparameter (controls scaling)
    r:     rank (controls capacity; typical: 8, 16, 32, 64)
```

The `alpha/r` scaling factor normalizes the contribution relative to rank so that changing `r` doesn't require retuning the learning rate.

**Why B=0 at initialization?** At training start, `A @ B = 0` (because B=0), so the LoRA side path contributes nothing. The model starts exactly as the pre-trained model, with no disruption. Training gradually moves B away from zero.

```text
At initialization:            After training:
  B = zeros → A @ B = 0        B = small values
  h = W @ x + 0 = W @ x        h = W @ x + (alpha/r) * A @ B @ x
  ↑ identical to base model     ↑ learned adaptation added on top
```

## Dimension Walkthrough

Let's trace the shapes through a LoRA-wrapped linear layer with concrete numbers:

```text
Example: d_model=8, r=2, alpha=4

Input x:  shape (8,)

─── Original path (frozen) ───────────────────────────────
W:        shape (8, 8)    ← 64 parameters, NOT updated
W @ x:    (8,8) @ (8,)  = (8,)    ← original transformation

─── LoRA side path (trainable) ────────────────────────────
B:        shape (2, 8)    ← 16 parameters, updated by optimizer
A:        shape (8, 2)    ← 16 parameters, updated by optimizer

Step 1:   B @ x  =  (2,8) @ (8,)  =  (2,)   ← project to rank-r space
Step 2:   A @ (B @ x)  =  (8,2) @ (2,)  =  (8,)   ← project back

Scale:    (alpha/r) * A @ (B @ x)  =  (4/2) * ...  =  2 * (8,)

─── Output ────────────────────────────────────────────────
h = W @ x  +  2 * A @ B @ x
    ─────     ───────────────
    (8,)         (8,)
         = (8,)  ← same shape as no-LoRA

Parameters: 64 (frozen) + 16 + 16 = 96 total
Trainable:  16 + 16 = 32   (33% of total, vs 100% in full fine-tuning)
```

In practice with d_model=4096, r=16:
- Original layer: 16,777,216 params — frozen
- LoRA: 65,536 + 65,536 = 131,072 params — trained
- Ratio: 0.78% of the original

## Applying LoRA to a Real Model

To apply LoRA to a transformer, you replace specific `nn.Linear` layers with `LinearWithLoRA`. Typically you target the attention projection matrices (Q, K, V, O) and sometimes the FFN layers. The transformer blocks are otherwise unchanged.

```text
Before LoRA:                          After LoRA:
─────────────────────────────────     ──────────────────────────────────────────
TransformerBlock                      TransformerBlock
  MultiHeadAttention                    MultiHeadAttention
    W_Q = Linear(768, 768)     →          W_Q = LinearWithLoRA(Linear(768,768), r=16)
    W_K = Linear(768, 768)     →          W_K = LinearWithLoRA(Linear(768,768), r=16)
    W_V = Linear(768, 768)     →          W_V = LinearWithLoRA(Linear(768,768), r=16)
    W_O = Linear(768, 768)     →          W_O = LinearWithLoRA(Linear(768,768), r=16)
  FeedForward                           FeedForward (unchanged, or also LoRA'd)
    w1 = Linear(768, 3072)                w1 = Linear(768, 3072)     ← often kept frozen
    w2 = Linear(3072, 768)                w2 = Linear(3072, 768)     ← often kept frozen
```

## Merging LoRA Back Into the Weights

After training, you have two options for the LoRA adapter:

**Option 1: Keep separate** — at inference time, compute `W @ x + (alpha/r) * A @ B @ x` for every forward pass. Slightly slower; requires carrying the LoRA matrices separately.

**Option 2: Merge into W** — compute `W_merged = W + (alpha/r) * A @ B` once, then inference is identical to a normal model. Zero extra compute at inference.

```text
Before merge:
  h = W @ x + (alpha/r) * A @ B @ x
      ^─────                 ^────────── two separate operations

After merge:
  W_merged = W + (alpha/r) * A @ B      ← computed ONCE, offline
  h = W_merged @ x                       ← single operation, same speed as base model
```

Merging is almost always the right choice for deployment. The base model weights are frozen, so the merge is a one-time, reversible operation.

## QLoRA: Quantize the Base, LoRA the Adapters

QLoRA (Dettmers et al. 2023) extends LoRA further: quantize the frozen base model weights to 4-bit (instead of 16-bit), keeping the LoRA adapter in 16-bit. The result:

```text
Memory comparison for LLaMA-7B:

  Full fine-tuning (FP16):   ~84 GB
  LoRA (FP16 base, r=16):    ~15 GB
  QLoRA (4-bit base, r=16):  ~5 GB   ← fits on a single 8GB GPU

  Quality degradation from FP16 → 4-bit base: surprisingly small
  (NF4 quantization preserves important weight distributions)
```

QLoRA made fine-tuning 7B models possible on consumer hardware. It's why you can fine-tune LLaMA on a single RTX 3090.

---

## When to Use LoRA

```text
Use LoRA when:
  + You have limited GPU memory (< 40GB for 7B models)
  + You want to maintain the pretrained base (can swap adapters)
  + You want to fine-tune quickly and cheaply
  + You're fine-tuning for a specific task/domain/style

Use full fine-tuning when:
  + You have abundant compute
  + The task is very different from pretraining (large distribution shift)
  + You need maximum performance and can afford the memory

In practice: LoRA is the default for almost everyone.
```

## Quick Recap

- Full fine-tuning requires 12 bytes × N params — prohibitive for large models.
- **LoRA** adds low-rank matrices `A` (d × r) and `B` (r × d) alongside frozen original weights. Only `A` and `B` are trained.
- Forward pass: `h = Wx + (α/r) · A(Bx)` — two paths, one frozen, one trainable.
- **B initialized to zeros**: guarantees the model starts identical to the pretrained checkpoint. Non-negotiable.
- Typical rank `r=16` on LLaMA-7B reduces trainable parameters from 7B to ~131M — about 53× reduction.
- After training, `W_merged = W + (α/r)·AB` can be computed once for zero-overhead inference.
- **QLoRA** adds 4-bit quantization of the base model, bringing 7B fine-tuning within reach of consumer GPUs (~5GB).

## Deep Dive: The Complete LoRA Math

**The core equation:**
Given frozen pretrained weights $W_0 \in \mathbb{R}^{d \times k}$, LoRA adds a trainable low-rank update:

$$W = W_0 + \Delta W = W_0 + \frac{\alpha}{r} BA$$

Where $B \in \mathbb{R}^{d \times r}$, $A \in \mathbb{R}^{r \times k}$, and $r \ll \min(d, k)$.

**Why this saves memory — the full accounting:**
Full fine-tuning with Adam requires storing per-parameter:
- Weights: 2 bytes (fp16)
- Gradients: 2 bytes
- Adam first moment: 4 bytes (fp32)
- Adam second moment: 4 bytes (fp32)

Total: 12 bytes per parameter.

LoRA only trains $B$ and $A$. Original weights are frozen (no gradients needed for them). The parameter reduction:

$$\frac{\text{LoRA params}}{\text{Full params}} = \frac{r(d+k)}{dk}$$

For $d = k = 4096$, $r = 8$: ratio $= \frac{8 \times 8192}{4096^2} \approx \frac{1}{256}$. A 256× reduction in trainable parameters, with a proportional reduction in gradient and optimizer state memory.

**Initialization — why start with $B = 0$:**
Standard initialization:

$$A \sim \mathcal{N}(0, \sigma^2), \quad B = 0$$

At initialization: $\Delta W = BA = 0$. The model starts with exactly the same behavior as the pretrained model. This means training starts from a meaningful baseline — the first gradient update is a small perturbation around known-good behavior, not a random jump.

**The $\alpha/r$ scaling:**
The $\alpha/r$ scaling factor controls the effective magnitude of the update:

$$\Delta W = \frac{\alpha}{r} BA$$

If you double $r$, the individual $BA$ product effectively doubles in magnitude (because $B$ and $A$ are now larger matrices). Dividing by $r$ keeps the update magnitude roughly constant regardless of rank choice. Common practice: set $\alpha = 2r$ (making the ratio 2) or $\alpha = r$ (making the ratio 1).

**What "rank" really means:**
LoRA assumes the optimal task adaptation lies in a low-dimensional subspace:

$$\text{rank}(\Delta W) \le r$$

This is not "the original weights $W_0$ are low rank." It's claiming "the change needed to adapt this model to your task is low rank." Empirically, this holds for most fine-tuning scenarios — the task update is a directional push in parameter space, not a random full-rank perturbation.

**PEFT method comparison:**

| Method | Where it modifies | Inference overhead | Merge possible |
|---|---|---|---|
| Prompt Tuning | Input embeddings | Uses context tokens | No |
| Prefix Tuning | Every layer's K/V | Extra compute per layer | No |
| Adapter | Bottleneck module in each block | Extra sequential compute | No |
| LoRA | Weight update (all linear layers) | None after merging | Yes |

**Merge — deploying LoRA with zero overhead:**
After training, you can fold LoRA back into the base weights:

$$W_{\text{merged}} = W_0 + \frac{\alpha}{r} BA$$

The result is a standard model with no extra layers or computation. The adaptation is baked in. Alternatively, keep $W_0$ separate and switch adapters dynamically — one base model, many specialized personalities, no memory overhead per adapter.

**QLoRA — fitting fine-tuning on a single GPU:**
Quantize the frozen base model to 4-bit:

$$h = Q(W_0)x + \frac{\alpha}{r} BAx$$

The quantized base model uses 4× less GPU memory. The LoRA adapters $A$ and $B$ are kept in full precision (bfloat16) — they're tiny, so the overhead is minimal. This made fine-tuning a 70B model possible on a single consumer GPU (with ~24GB VRAM), which was previously impossible.

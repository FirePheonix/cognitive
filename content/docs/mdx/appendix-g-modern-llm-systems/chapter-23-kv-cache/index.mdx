# 23. KV Cache

Every time the model generates a new token, it runs a full forward pass. Inside that forward pass, at every attention layer, it computes three vectors for every token in the sequence — Q, K, and V. Then it computes attention scores between all pairs. Then it does the weighted sum.

That's a lot of work. And here's the thing: most of it is work you already did one step ago.

---

## The Redundant Computation Problem

Let's trace what happens when generating the fourth token of a sequence.

```text
Generating token 4 ("the"):

  Input so far:  ["The", "cat", "sat"]
  
  Attention layer needs to compute, for all positions:
    K₁ = W_K × embedding("The")    ← computed at step 1, 2, 3
    K₂ = W_K × embedding("cat")    ← computed at step 2, 3
    K₃ = W_K × embedding("sat")    ← computed at step 3
    K₄ = W_K × embedding(new)      ← actually new
    
    V₁ = W_V × embedding("The")    ← computed at step 1, 2, 3
    V₂ = W_V × embedding("cat")    ← computed at step 2, 3
    V₃ = W_V × embedding("sat")    ← computed at step 3
    V₄ = W_V × embedding(new)      ← actually new
  
  You need all 8 vectors. But 6 of them you've computed before.
```

The only genuinely new work at step `t` is computing `K_t` and `V_t` for the one new token. Everything before position `t` is repetition.

How much repetition? Across the whole generation:

```text
Cumulative attention computation at each step (no cache):

  Step 1:   compute K₁, V₁              →  1 new K/V pair
  Step 2:   compute K₁, V₁, K₂, V₂     →  1 new + 1 repeated
  Step 3:   compute K₁..K₃, V₁..V₃     →  1 new + 2 repeated
  Step t:   compute K₁..Kₜ, V₁..Vₜ     →  1 new + (t-1) repeated
  
  Total K/V computations for N tokens:   1 + 2 + 3 + ... + N = N(N+1)/2

  Avoidable work (repeated prefix):      N(N+1)/2 - N  =  N(N-1)/2

  At N=100:   5,050 total,  4,950 avoidable   → 98% waste
  At N=1,000: 500,500 total, 499,500 avoidable → 99.8% waste
```

The waste grows with sequence length. At 1,000 tokens, **99.8% of all K/V computation is re-doing work from previous steps**.

---

## The Fix: Store and Reuse

The KV cache stores the K and V tensors for every token that has already been processed. When the next token is generated:

1. Compute K and V only for the **new** token
2. **Append** them to the cache
3. Use the full cached K and V history for the attention computation

![Without a KV cache, step 4 recomputes K and V for every previous token. With the cache, those tensors are reused and only the new position is computed. Same attention math, N× less K/V work by step N.](/appendix-g/23-kv-cache/kv-cache-reuse.png)

![Decode as q₄ K_cacheᵀ. Cached K for The/cat/sat is 3×4; the new key is appended to 4×4. The new query (1×4) times Kᵀ (4×4) is one score row. Worked: q₄ · k_sat = [1,1,0,2]·[1,0,0,1] = 3. Then softmax and weights × V — another 1×d multiply, not a full n×n map.](/appendix-g/23-kv-cache/qk-cache-matmul.png)

The outputs are **mathematically identical**. This isn't an approximation — it's memoization. The values stored in the cache are the exact same numbers you would have computed anyway.

## The Memory Cost

The KV cache trades compute for memory. For every token in the context, for every layer, the cache stores one K vector and one V vector.

```text
KV cache size per token:

  Per layer:   2 vectors (K and V) × n_heads × d_k × bytes_per_value
  All layers:  n_layers × per_layer_cost

  GPT-2 small (n_layers=12, n_heads=12, d_k=64, float16 = 2 bytes):
    Per layer:  2 × 12 × 64 × 2 bytes = 3,072 bytes = 3 KB
    All layers: 12 × 3 KB = 36 KB per token
    
    At 1,024 tokens:  36 KB × 1,024 = 36 MB       ← manageable
    At 8,192 tokens:  36 KB × 8,192 = 288 MB      ← still fine

  LLaMA-2 70B (n_layers=80, n_heads=64, d_k=128, float16):
    Per layer:  2 × 64 × 128 × 2 bytes = 32,768 bytes = 32 KB
    All layers: 80 × 32 KB = 2,560 KB = 2.5 MB per token
    
    At 4,096 tokens (one request): 2.5 MB × 4,096 = 10 GB
    At 32 concurrent requests:     10 GB × 32     = 320 GB  ← bigger than the model!

This is why long-context inference is expensive:
the KV cache, not the model weights, becomes the binding memory constraint.
```

## GQA and MQA: Shrinking the Cache

A natural response to the memory problem: what if not every head needs its own K/V?

**Multi-Query Attention (MQA)**: all heads share a single K and V. Query heads remain separate. This cuts KV cache to `1/n_heads` of its original size.

**Grouped-Query Attention (GQA)**: groups of heads share K/V. A middle ground — better quality than MQA, much smaller cache than full MHA.

```text
MHA (standard):        8 query heads, 8 key heads, 8 value heads
  KV cache per token:  8 K vectors + 8 V vectors  = 16 vectors

GQA (groups of 2):     8 query heads, 4 key heads, 4 value heads
  KV cache per token:  4 K vectors + 4 V vectors  = 8 vectors  ← 2× smaller

MQA:                   8 query heads, 1 key head,  1 value head
  KV cache per token:  1 K vector  + 1 V vector   = 2 vectors  ← 8× smaller

Quality:   MHA > GQA > MQA  (marginal difference with good training)
Cache:     MHA >> GQA >> MQA

LLaMA-3, Mistral, Gemini all use GQA.
```

---

## Quick Recap

- During decode, every step recomputes K and V for all previous tokens. At 1,000 tokens, 99.8% of this is redundant.
- **KV cache** stores K and V from all past positions. Each new decode step computes only K/V for the one new token. Output is mathematically identical — not an approximation.
- **Memory cost**: grows as `2 × n_layers × n_heads × d_k × seq_len`. At scale (70B model, 8K context, 32 concurrent requests), this exceeds the model weights themselves.
- **GQA/MQA** shrink the cache by sharing K/V across attention heads. LLaMA-3 and Mistral use GQA — same quality, 2–4× smaller cache.
- The memory pressure from long KV caches is the main motivation for the PagedAttention system described in Chapter 26.

# 27. Chain-of-Thought and Reasoning Models

A transformer has a fixed number of layers. Every input token goes through the same number of operations before the model produces an output. This creates a hard ceiling: the amount of *thinking* the model can do is proportional to the number of layers, and that's fixed at training time.

For simple tasks — "What's the capital of France?" — this is fine. The answer is a retrieval, not a computation. But for multi-step reasoning, this architectural constraint becomes a real problem.

---

## The Reasoning Gap

Consider: **357 × 289 = ?**

A human doing this mentally performs a sequence of steps: `357 × 200 = 71,400`, `357 × 80 = 28,560`, `357 × 9 = 3,213`, then adds. The answer emerges from a *process*.

A transformer doing this in one forward pass has to arrive at `103,173` by pattern matching — it's essentially guessing based on what answers to similar-looking problems appeared in training data. If `357 × 289` never appeared, it has to generalize, and that generalization fails more often than it should.

```text
The fixed-depth problem:

  Input → embedding → 96 transformer layers → output "103173"
              ↑                  ↑
         same for          same compute
         every input         budget always
  
  A 2-digit multiplication and a 10-step proof get the same
  number of computation steps. The proof needs more — it can't have it.
  
  Result: models that are brilliant at pattern matching
          but fail at tasks requiring extended step-by-step computation
```

---

## Chain-of-Thought: Writing Steps Into Context

The fix is elegant: instead of asking the model to produce the answer directly, ask it to write out its reasoning first. Each reasoning step becomes part of the context — and the next step is generated by attending to all previous steps.

```text
WITHOUT chain-of-thought:
  Q: What is 357 × 289?
  A: 95,795   ← wrong guess (correct: 103,173)

WITH chain-of-thought:
  Q: What is 357 × 289? Think step by step.
  
  A: Let me work through this:
     357 × 200 = 71,400
     357 × 80  = 28,560
     357 × 9   =  3,213
     Sum: 71,400 + 28,560 = 99,960
          99,960 + 3,213  = 103,173
     
     The answer is 103,173.   ← correct ✓
```

The mechanism: each intermediate result becomes context for the next computation step. What would require 10 "layers" of reasoning internally now happens across 10 *sequential token predictions*, each of which only needs to produce one step correctly.

```text
Chain-of-thought transforms:
  
  "one hard forward pass" → "many easy forward passes in relay"
  
  Step 1: model sees [question]                → outputs "Let me work through this:"
  Step 2: model sees [question + step 1]       → outputs "357 × 200 = 71,400"
  Step 3: model sees [question + step 1 + 2]   → outputs "357 × 80  = 28,560"
  ...
  Step 8: model sees [everything so far]       → outputs "The answer is 103,173."
  
  At each step: the transformer only needs to compute ONE arithmetic fact.
  That's easy. The hard part (tracking state across many steps) is offloaded
  to the context window.
```

## Few-Shot vs Zero-Shot CoT

**Few-shot CoT**: provide worked examples in the prompt. Show the model how to reason step-by-step before asking your question.

```text
Few-shot CoT prompt:

  Q: Natalia sold clips to 48 of her friends in April and then sold
     half as many clips in May. How many clips did she sell altogether?
  A: Natalia sold 48/2 = 24 clips in May.
     Natalia sold 48 + 24 = 72 clips altogether.
     The answer is 72.

  Q: Weng earns $12 per hour babysitting. Yesterday, she just did
     5.5 hours of babysitting. How much did she earn?
  A: [model imitates the format and reasons step by step]
```

**Zero-shot CoT**: just append "Let's think step by step." — no examples needed. Surprisingly effective.

```text
Zero-shot CoT:

  Q: If there are 3 cars in the parking lot and 2 more cars arrive,
     how many cars are in the parking lot?
  
  WITHOUT magic phrase:    "5"         ← often correct by luck
  
  WITH "Let's think step by step":
  A: Let's think step by step.
     Initially there are 3 cars.
     2 more arrive: 3 + 2 = 5.
     There are 5 cars.   ← correct, with shown work
  
The phrase activates reasoning format learned during training — the model
has seen millions of examples of step-by-step solutions and knows to imitate them.
```

## Self-Consistency: Sample Many, Vote on Best

A single CoT chain can still go wrong — the model might take a wrong reasoning path and confidently arrive at a wrong answer. **Self-consistency** fixes this by sampling multiple chains and voting.

```text
SELF-CONSISTENCY:

  Ask the same question N times (with temperature > 0 to get diverse chains).
  Each chain reasons independently and arrives at an answer.
  Take the MAJORITY VOTE.
  
  Example (N=5):
    Chain 1: ...calculation A...  → answer 103,173  ✅
    Chain 2: ...different path...  → answer 103,173  ✅
    Chain 3: ...arithmetic error... → answer 97,450  ✗
    Chain 4: ...calculation B...  → answer 103,173  ✅
    Chain 5: ...different path...  → answer 103,173  ✅
    
    Majority vote: 103,173 (4/5)  → CORRECT

Why this works: wrong paths are diverse (errors are random).
Correct paths tend to converge on the same answer.
Majority vote cancels out errors.

Tradeoff: N× more inference cost for reliability.
Best for: high-stakes tasks where accuracy matters more than cost.
```

## Thinking Models: Training for Reasoning

Few-shot CoT is a prompt-engineering trick. But the most capable modern reasoning models don't need special prompting — they were explicitly **trained** to reason.

**How o1 and DeepSeek-R1 work:**

```text
Standard LLM (GPT-4, LLaMA-3):
  Training signal: "predict the next token correctly"
  What it learns: patterns in text, including some reasoning patterns
  At inference: generates one response, done

Thinking model (o1, DeepSeek-R1):
  Training stage 1: supervised fine-tuning on reasoning traces
                    (human-written or distilled from strong models)
  Training stage 2: reinforcement learning on VERIFIABLE tasks
                    (math problems, coding challenges, logic puzzles)
    
    Reward signal:
      correct final answer → positive reward
      wrong final answer   → no reward
      (the intermediate reasoning is not directly supervised)
    
    What the model learns:
      How to explore, backtrack, self-check, and try multiple approaches
      — because these strategies correlate with correct final answers
    
  At inference: generates an internal <thinking> chain, THEN the answer
```

```text
DeepSeek-R1 key finding:
  RL on verifiable tasks alone → model spontaneously develops
  "aha moment" behaviour: self-correction, verification loops,
  and extended exploration — WITHOUT being told to do these things.
  
  The model learned that longer, more careful reasoning correlates with
  correct answers on math and coding benchmarks.
  More thinking → more reward → model learns to think more.
  
  Emergent behaviour from simple reward shaping.
```

## Test-Time Compute Scaling

An important insight that's reshaping how the field thinks about scaling:

```text
TRAINING-TIME SCALING (traditional):
  More parameters → better model
  More training data → better model
  More training compute → better model
  
  Diminishing returns: doubling parameters gives <2× improvement
  Very expensive: each scale-up requires retraining from scratch

TEST-TIME COMPUTE SCALING (newer):
  Same model + more inference compute → better answers
  
  How:
    - Generate K candidate answers, pick best (Best-of-N)
    - Use a longer chain of thought (more reasoning steps)
    - Run multiple reasoning paths and verify (self-consistency)
    - MCTS-style tree search over possible reasoning paths
  
  Key property: can be applied at inference time, per-query
  Expensive queries get more compute; cheap queries get less
```

```text
Empirical result (OpenAI o1):
  
  On competition math (AIME 2024):
    GPT-4o:        13.4% (standard generation)
    o1 (standard): 74.4% (thinking model, standard budget)
    o1 (high comp): 83%  (same model, more thinking time allowed)
  
  The accuracy gap between o1-standard and o1-high-compute comes
  entirely from more test-time compute on the SAME model weights.
  
  This suggests a new scaling axis: not just parameters and data,
  but reasoning depth at inference time.
```

## Quick Recap

- Transformers have **fixed compute depth** per forward pass. Multi-step reasoning exceeds this budget.
- **Chain-of-thought** writes intermediate steps into the context. Each step only needs one easy prediction; the context window handles state tracking across steps.
- **Zero-shot CoT**: just append "Let's think step by step." Activates learned reasoning format from training data.
- **Self-consistency**: sample N reasoning chains, take the majority vote answer. Wrong paths are diverse (random errors), correct paths converge. Trades inference cost for accuracy.
- **Thinking models** (o1, DeepSeek-R1): trained with RL on verifiable tasks. Learn to explore, backtrack, and self-verify — behaviors that emerge from optimizing for correct final answers.
- **Test-time compute scaling**: same model weights + more inference compute → better answers. Per-query scaling. A new axis of improvement alongside parameter and data scaling.

## GRPO and Modern Reasoning RL

### Self-Consistency — the Simplest Test-Time Boost

Instead of generating one reasoning path, generate $K$ different ones (using temperature sampling), then take the majority vote:

$$\hat{y} = \arg\max_y \sum_{k=1}^{K} \mathbf{1}[y^{(k)} = y]$$

Intuition: if 7 out of 10 independently generated reasoning paths reach the same answer, it's probably right. This is test-time ensembling. Cost: $K$ times the inference compute. Benefit: often a 5–15% accuracy improvement on reasoning benchmarks with $K=10$.

### Test-Time Compute as a New Scaling Axis

A key realization from 2024–2025: you don't only scale capabilities by making models bigger and training longer. You can also scale at inference time:

$$\text{Performance} = f(\text{training compute},\ \text{test-time compute})$$

Test-time compute can mean: longer reasoning chains (more reasoning tokens), multiple samples + voting (self-consistency), structured search (Tree-of-Thought, MCTS), or iterative refinement (generate → verify → revise).

This is what o1/o3 and similar models do: they "think for longer" on hard problems by generating extended internal reasoning before answering.

### Why RL Works for Math and Code — Verifiable Rewards

For tasks like math and coding, you can verify correctness programmatically:

$$r(x, y) = \mathbf{1}[\text{verify}(y) = \text{correct}]$$

Run unit tests on code. Check if the math answer equals the ground truth. This gives a binary, unambiguous, scalable reward signal — which is exactly what RL needs. The model can self-improve by generating solutions and automatically filtering/reinforcing the ones that pass verification.

Open text generation doesn't have this luxury — "is this a good paragraph?" has no easy automated verifier. This is why reasoning RL has been most successful in math and code.

### GRPO — the Efficient RL Algorithm for Reasoning

GRPO (Group Relative Policy Optimization) sidesteps the need for a separate critic/value network:

1. Sample $G$ responses to the same question: $y_1, \dots, y_G$
2. Score each with a reward function
3. Normalize rewards within the group:

$$A_i = \frac{r_i - \mu_G}{\sigma_G + \epsilon}$$

4. Responses above group average get positive advantage; below get negative

The key: no separate value model needed. Group normalization provides the baseline automatically. This makes GRPO much simpler and cheaper than PPO while achieving comparable or better results for reasoning tasks.

### PPO vs GRPO

| | PPO | GRPO |
|---|---|---|
| Value model | Required (trained separately) | Not needed |
| Advantage estimate | Critic network | Group-relative normalization |
| Complexity | Higher | Lower |
| Best for | General RLHF | Reasoning/verifiable tasks |

# 26. Inference Systems at Scale

The previous three chapters covered token-level optimizations — KV cache, quantization, and speculative decoding. Each of those operates on a single request in isolation.

When you're serving thousands of users simultaneously, a whole new set of problems appears. Requests arrive at different times and have different lengths. Some are short questions; some are long document analyses. Some finish in two seconds; some run for minutes. The GPU has finite memory. How do you keep it full and efficient?

This chapter is about the systems layer: how real inference servers handle concurrent requests.

---

## The Two Phases of LLM Inference

Every LLM request has two distinct phases with completely different computational profiles:

![Prefill vs decode, then PagedAttention: the KV cache is split into fixed-size blocks (like OS pages) so a request's tokens can live anywhere in GPU memory instead of one contiguous slab that fragments.](/appendix-g/26-inference-systems-at-scale/prefill-decode-paging.png)

**Prefill** processes the whole prompt in one parallel forward pass — compute-heavy, high GPU utilization, duration proportional to prompt length (a 1,000-token prompt might take ~0.3s).

**Decode** emits one token per forward pass — memory-bandwidth-heavy, often 30–50% of peak GPU, duration = response length × latency per token (500 tokens at 30ms is 15 seconds).

These two phases have different resource requirements. Prefill wants GPU compute. Decode wants memory bandwidth and low-latency KV cache access. This mismatch is one reason serving LLMs efficiently is hard.

## Service Metrics: What You're Actually Optimizing For

Before designing a system, you need to know what to measure.

```text
TTFT  — Time To First Token
  The time from sending the request to receiving the first token.
  Dominated by: prefill phase duration.
  Why it matters: the user is staring at a blank screen during this time.
  Users experience TTFT > 5 seconds as "slow".

TPOT  — Time Per Output Token
  Average time between successive tokens during generation.
  Dominated by: decode phase latency.
  Why it matters: this is the "streaming speed" the user sees.
  < 50ms per token feels smooth; > 100ms feels choppy.

Throughput
  Total tokens generated per second, across all concurrent requests.
  Operator metric: determines cost per query.
  Higher throughput = cheaper to serve.

Concurrency
  Number of requests being processed simultaneously.
  Constrained by: KV cache memory (each request's cache must fit in GPU VRAM).
```

```text
The fundamental tension:

  Batching many requests together → higher throughput (GPU more utilized)
                                  → higher TTFT (each request waits for others)
  
  Processing requests immediately → lower TTFT (user sees fast response)
                                  → lower throughput (GPU underutilized)

  This is the standard throughput vs. latency tradeoff in distributed systems.
  Inference servers navigate it by batching what they can while staying within
  latency budgets.
```

## The Memory Fragmentation Problem

Naive serving allocates a contiguous memory block for each request's KV cache. This causes two types of waste:

```text
INTERNAL FRAGMENTATION:
  Request needs 437 tokens of KV cache.
  System rounds up to next block boundary: 512 tokens allocated.
  75 tokens of memory wasted inside the allocation.

EXTERNAL FRAGMENTATION:
  Requests finish at different times, leaving gaps in memory.
  
  Memory layout after several requests complete:
  
  [REQ_A: 300 tok][ FREE: 200 tok ][REQ_C: 400 tok][FREE: 180 tok][REQ_E: 250 tok]
  
  Total free: 200 + 180 = 380 tokens of space.
  New request needs 350 tokens.
  Can it run?  NO — no single contiguous block has 350 free.
  Despite 380 tokens free total, it can't fit.
  
  This is the same problem as RAM fragmentation in an OS from the 1970s.
```

At scale, fragmentation can waste 30–40% of available KV cache memory. That directly translates to fewer concurrent requests and lower throughput.

## PagedAttention: Borrowing from Operating Systems

The insight from the vLLM paper (Kwon et al. 2023): LLMs have the same memory management problem that operating systems solved with virtual memory. Use the same solution.

```text
OS virtual memory:
  Physical RAM divided into fixed-size PAGES (e.g., 4 KB each).
  Each process gets a virtual address space with a PAGE TABLE.
  Page table maps: virtual page number → physical page frame.
  Allocate pages on demand. Pages of one process can be anywhere in RAM.
  No fragmentation (physical pages are all the same size).

PagedAttention applies this to KV cache:
  KV cache divided into fixed-size BLOCKS (e.g., 16 tokens of K+V each).
  Each request gets a logical block table.
  Block table maps: logical block index → physical block location in GPU memory.
  Allocate blocks on demand. A request's blocks can be anywhere in GPU memory.
  No fragmentation (all blocks are identical size).
```

The figure at the top of this chapter is that layout: contiguous slabs fragment; fixed-size KV blocks can sit anywhere, so a new request takes any free blocks.

## Continuous Batching

Traditional batch inference waits for all requests in a batch to finish before starting the next batch. Since LLM responses vary wildly in length, this creates a "convoy problem":

```text
STATIC BATCHING (traditional):

  Batch of 4 requests:
  Request A: ████████████████████████████ 28 tokens
  Request B: ██████ 6 tokens
  Request C: ████████████████ 16 tokens
  Request D: ████████████████████████████████ 32 tokens
  
  ← GPU waits here for D to finish, even though A,B,C are done →
  
  GPU utilization:
  Time 0-6:    all 4 requests running        → 100%
  Time 6-16:   3 requests running (B done)   →  75%
  Time 16-28:  2 requests running (C done)   →  50%
  Time 28-32:  1 request running (A done)    →  25%
  
  Average: ~62.5% GPU utilization
  Batches B, C, A are all blocked waiting for D.
```

```text
CONTINUOUS BATCHING:

  New requests join the batch as soon as any slot frees up.
  
  Batch starts with A, B, C, D.
  At time 6: B finishes → E immediately takes its slot.
  At time 16: C finishes → F immediately takes C's slot.
  At time 28: A finishes → G immediately takes A's slot.
  
  GPU always has 4 concurrent requests running.
  Average utilization: ~95%+ (limited only by request arrival rate)
  
  Also called "in-flight batching" or "iteration-level scheduling".
```

This is a significant operational win. You go from ~62% utilization to ~95% just by scheduling smarter. At production traffic, this can halve the cost of serving.

## Prefix Caching

Many requests share a common prefix — the system prompt. Every conversation with ChatGPT starts with the same system instructions. Every API call from the same application sends the same context preamble.

Computing the KV cache for that common prefix is redundant work done identically for every single request.

```text
WITHOUT prefix caching:
  Request 1: system_prompt(1000 tokens) + user_query(50 tokens)
    → prefill 1050 tokens → compute KV cache for all 1050 tokens
  
  Request 2: system_prompt(1000 tokens) + different_query(40 tokens)
    → prefill 1040 tokens → compute KV cache for all 1040 tokens again
    
  The first 1000 tokens of KV cache are identical but computed twice.

WITH prefix caching:
  First request:  compute + cache KV for system_prompt
  Second request: hit cache → skip prefill for system_prompt
                  only prefill the 40 new query tokens
  
  Saved: 1000 tokens × model_forward_cost per request that hits the cache
  Latency reduction: TTFT drops from ~300ms to ~10ms for cached requests
```

Real systems report 70-90% cache hit rates for API traffic, since most requests to any given application share the same system prompt.

## Prefill/Decode Disaggregation

The mismatch between prefill (compute-bound) and decode (bandwidth-bound) can be exploited at the hardware level:

```text
DISAGGREGATED SERVING:

  Prefill cluster:  high-compute GPUs (good at matrix multiplication)
                    → handle all prompt processing
                    → ship resulting KV cache to decode cluster

  Decode cluster:   high-bandwidth GPUs (good at memory reads)
                    → handle all token generation
                    → use shipped KV cache
  
  Result:  each cluster can be independently scaled
           right-size compute for workload
           better utilization of each GPU type
  
  Used by: large-scale production deployments (Meta, Google)
  Downside: KV cache transfer adds latency between phases
```

## Quick Recap

- **Prefill** (prompt) is compute-intensive and parallel. **Decode** (generation) is bandwidth-intensive and serial. They have different optimal hardware profiles.
- **TTFT** (time to first token) is dominated by prefill. **TPOT** (time per output token) is dominated by decode. Both matter to users; throughput matters to operators.
- **Memory fragmentation** in naive KV cache allocation wastes 30–40% of GPU memory — some of it internal (rounding), some external (scattered gaps).
- **PagedAttention** applies OS virtual memory paging to KV cache: fixed-size blocks, logical-to-physical block table, no fragmentation. Core innovation in vLLM.
- **Continuous batching** starts new requests immediately when slots free up, instead of waiting for the whole batch. Raises GPU utilization from ~60% to ~95%.
- **Prefix caching** reuses KV cache for shared prompt prefixes. 70-90% cache hit rates in practice → dramatic TTFT reduction for repeat prefixes.
- **Prefill/decode disaggregation** runs the two phases on separate GPU clusters optimized for each, enabling better resource utilization at large scale.

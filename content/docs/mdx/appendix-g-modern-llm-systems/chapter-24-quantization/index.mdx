# 24. Quantization

GPT-3 has 175 billion parameters. In float32, that's 700 GB of just weights. No single GPU has 700 GB. Even in float16, it's 350 GB — still too large for most machines.

Quantization is the technique that makes large models runnable on real hardware. The idea: instead of storing each weight as a 32-bit or 16-bit float, store it as an 8-bit or 4-bit integer. Smaller numbers, less memory, faster to read from GPU memory. The cost is a small loss in precision — but in practice, carefully quantized models lose very little quality.

---

## Why Integers? A Bit of Background

Neural network computations are fundamentally floating-point. Floats can represent a huge range of values — from tiny (1e-38) to huge (3e38) — and any value in between. This flexibility is what makes training stable.

But at inference time, you don't need that full range. A trained model's weights have settled into a distribution that's much narrower. You can approximate that distribution with integers if you're smart about the mapping.

![Symmetric int8: scale = max|x| / 127, q = round(x / scale) clipped to [−127, 127], x̂ = q × scale. A worked example maps [0.50, −1.20, 0.80, −0.30, 2.10] onto integers and back with tiny error. Beside it, memory for real models in fp16 vs int8 vs int4.](/appendix-g/24-quantization/int8-and-memory.png)

float16 uses 1 sign + 5 exponent + 10 mantissa bits (range ±65,504). int8 is 256 distinct values in [−128, 127]. A typical transformer weight matrix lives roughly in [−2, 2] — map that range onto [−127, 127] and you can store it as int8. The question: how do you do that mapping well?

---

## Symmetric Quantization

The simplest approach: find the absolute maximum value in the tensor, use it to set a scale, then round everything to integers.

```text
SYMMETRIC INT8 QUANTIZATION:

  scale  =  max(|x|) / 127

  quantize:   q = round(x / scale)   clipped to [-127, 127]
  dequantize: x̂ = q × scale

Example:
  x     = [ 0.50,  -1.20,  0.80,  -0.30,   2.10]
  
  max|x| = 2.10
  scale  = 2.10 / 127 = 0.01654
  
  q      = round(x / 0.01654)
         = [ 30,   -73,   48,   -18,   127]   ← integers in [-127, 127]
  
  x̂     = q × 0.01654
         = [ 0.496, -1.207,  0.794, -0.298,  2.100]
  
  Error  = x - x̂
         = [ 0.004, -0.007,  0.006, -0.002,  0.000]   ← tiny
```

The rounding introduces small errors. The larger the scale (bigger range of values), the coarser the quantization grid, the bigger the errors.

```text
Why the range matters:
  
  Input range [-2, 2], 256 grid points:
    Grid spacing = 4 / 256 = 0.016   ← fine, small error
  
  Input range [-0.1, 0.1], 256 grid points:
    Grid spacing = 0.2 / 256 = 0.00078   ← very fine, tiny error
  
  Input range [-100, 100] with mostly values near zero:
    Grid spacing = 200 / 256 = 0.78   ← coarse, large error for small values
```

That last case is the **outlier problem** — a single extreme value in one channel stretches the scale and destroys precision for all the other values.

## Asymmetric Quantization

If your data isn't centered around zero, symmetric quantization wastes half the integer range. Post-activation values (after ReLU/GELU) are always positive — mapping them to `[-127, 127]` wastes the entire negative side.

Asymmetric quantization fixes this with a **zero point** — an offset that shifts the integer range to match the actual data distribution.

```text
ASYMMETRIC UINT8 QUANTIZATION:

  scale    =  (x_max - x_min) / 255
  zero_pt  =  x_min

  quantize:   q = round((x - x_min) / scale)   clipped to [0, 255]
  dequantize: x̂ = q × scale + x_min

Example (post-ReLU, all positive with one outlier):
  x     = [5.00,  0.04,  0.19,  0.46,  0.07]
  
  x_min = 0.04,   x_max = 5.00
  scale = (5.00 - 0.04) / 255 = 0.01941
  
  q     = round((x - 0.04) / 0.01941)
        = [255,    0,     8,    22,    2]   ← full [0, 255] range used
  
  x̂    = [5.000, 0.040, 0.195, 0.467, 0.079]
```

```text
SYMMETRIC vs ASYMMETRIC — which uses integers better:

  Post-ReLU data: [5.00, 0.04, 0.19, 0.46, 0.07]
  
  Symmetric:
    scale = 5.00/127 = 0.0394
    q     = [127,  1,  5, 12,  2]
    Integer range used: 1 to 127  (positive side only, negative side WASTED)
    MAE   = 0.0056

  Asymmetric:
    q     = [255,  0,  8, 22,  2]
    Integer range used: 0 to 255  (full range, 0% wasted)
    MAE   = 0.0048  ← slightly better
  
  For weights (symmetric around 0): symmetric works fine
  For activations (often shifted):  asymmetric is better
```

## Quantization Granularity: One Scale or Many?

The scale determines how well the integer grid covers the actual values. One scale for the whole matrix is simple — but a single outlier row can ruin precision for every other row.

```text
GRANULARITY OPTIONS:

  Per-tensor:  one scale for the entire weight matrix
    + Simplest to implement
    - One outlier channel destroys precision for all channels

  Per-channel: one scale per row of the weight matrix
    + Each channel gets its own calibrated range
    + Standard for INT8 weight quantization
    - More scales to store and apply

  Per-group:   one scale per small group (e.g., 128 values) within each row
    + Finest granularity — handles sub-row variation
    + Required for 4-bit quantization (GPTQ, AWQ)
    - More overhead, but worth it at 4 bits

  Concrete example — 4×8 weight matrix where row 0 has 8× larger values:
    per-tensor:   MAE = 0.0207
    per-channel:  MAE = 0.0073   ← 2.8× better
    per-group(4): MAE = 0.0047   ← 4.4× better
```

## The Outlier Problem and Why Naive 4-bit Fails

Going from INT8 to INT4 (only 16 possible values instead of 256) seems like it should be straightforward — just repeat the same process with fewer bits. But it doesn't work well in practice.

The reason: transformer activations have **outlier channels** — a small number of dimensions that have values much larger than the rest. These few channels dominate the scale and crush precision for all the others.

```text
INT4 range: [-8, 7] or [0, 15]  — only 16 distinct values
Grid spacing with outlier: 10× larger than without
Small-magnitude channels: effectively only 1-2 distinct values

Result: catastrophic quality loss if you just round to INT4
```

Two algorithms solve this — **GPTQ** and **AWQ**:

```text
GPTQ (Frantar et al. 2022):
  Idea: use second-order information (Hessian) to compensate for errors
  
  When quantizing weight w:
    1. Round w → q  (introduces rounding error ε = w - q×scale)
    2. Redistribute ε across other weights in the same row
       using the Hessian to minimize the total output change
    3. The model "absorbs" the quantization error rather than accumulating it
  
  Result: 4-bit weights with near-INT8 quality
  Used by: most 4-bit models on Hugging Face (TheBloke's GPTQ releases)

AWQ (Lin et al. 2023):
  Idea: protect the important channels by scaling BEFORE quantization
  
  Key observation: not all weights matter equally — channels corresponding
  to larger activations matter more (they contribute more to the output)
  
  Per-channel scale:  w_scaled = w × s,   then quantize w_scaled
  Dequantize:         w_hat    = q × (scale / s)
  
  The important channels get scaled up → finer quantization grid for them
  → less error exactly where it matters most
  
  Result: similar quality to GPTQ, often faster to apply
  Used by: many quantized models (LLaMA, Mistral AWQ releases)
```

## Quick Recap

- Quantization maps float weights to integers: fewer bits → smaller model → faster memory reads.
- **Symmetric** quantization: `scale = max|x| / 127`, `q = round(x / scale)`. Simple, wastes negative half for non-negative data.
- **Asymmetric** quantization: `scale = (x_max - x_min) / 255`, uses a zero point. Fits the full integer range to the actual data distribution. Better for activations.
- **Granularity**: per-tensor (one scale for everything) → per-channel (one per row) → per-group (one per 128 elements). Finer granularity = less error, especially with outlier channels.
- **INT4 naive rounding fails** because outlier channels dominate the scale. GPTQ (second-order compensation) and AWQ (activation-aware scaling) fix this — enabling near-INT8 quality at 4 bits.
- **Real impact**: int4 LLaMA-7B uses 3.5 GB — fits on a consumer GPU. That's why local LLM inference became accessible.
